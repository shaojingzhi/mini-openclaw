# Mini-OpenClaw 改进版 PRD

## 1. 文档目标

本文档用于定义 Mini-OpenClaw 下一阶段最重要的产品与工程改进方向，目标不是继续堆砌“功能点”，而是把当前项目从“可演示的 Agent 原型”推进到“适合写进简历、可被面试官认可的工程化 AI Agent 项目”。

本文档基于以下输入整理：

- 当前仓库已有能力：`FastAPI + Next.js + LangGraph + 文件记忆 + 本地工具调用 + 前端工作区`
- `references/chat-with-deepseek.txt` 中提炼出的高优先级改进建议
- 当前项目定位：本地优先、透明可控、文件即记忆、适合作为通用 Agent 底座

---

## 2. 项目现状判断

### 2.1 已有优势

- 已具备完整的前后端骨架，可实际运行和演示
- 已实现较清晰的 Agent 工作区形态，包括 `memory / skills / workspace files`
- 已有透明化记忆方案，区别于纯黑盒向量数据库
- 已具备一定的 Agent 工具调用与文件编辑能力

### 2.2 当前短板

当前项目最主要的问题不是“不能跑”，而是“缺乏可量化、可论证、可解释的工程闭环”。面试官最容易追问的点包括：

- Agent 到底效果怎么样，如何评估？
- 出错后如何诊断？
- 多会话/多用户上下文是否会混淆？
- 为什么这个项目不是一个玩具？
- 与成熟 Agent 相比，你的设计价值在哪里？

---

## 3. 本阶段核心目标

本阶段只聚焦 5 个高价值改进方向：

1. 建立 Agent 离线评测体系
2. 建立运行可观测性能力
3. 实现最小可行多用户隔离
4. 建立失败分析与异常兜底机制
5. 落地一个垂直场景 Demo

### 3.1 成功定义

如果本阶段完成，Mini-OpenClaw 应该满足以下目标：

- 可以展示一套结构化评测报告，而不是只展示聊天界面
- 可以追踪每次运行的成本、延迟、工具调用和错误
- 可以说明系统如何避免不同用户/会话的记忆污染
- 可以对失败进行归因，而不是“模型偶尔会错”
- 可以用一个具体场景证明项目能解决真实问题

---

## 4. 非目标

本阶段明确不做以下事项：

- 不做重量级 SaaS 化改造
- 不做完整的注册/登录/邮箱验证体系
- 不做 PostgreSQL + Redis + OAuth 的复杂生产栈
- 不做与 OpenClaw 的通用能力正面对标
- 不以“超过 SOTA Agent”为目标

本阶段的关键词是：可证明、可解释、可演示、可写简历。

---

## 5. 用户与使用场景

### 5.1 目标用户

- AI Agent 岗位面试官
- 自己未来的面试场景
- 希望验证 Agent 工程方法论的开发者
- 需要本地透明 Agent 工作区的个人用户

### 5.2 核心场景

- 展示 Agent 的工具调用、文件记忆与技能机制
- 展示一个完整的“从提问到执行到诊断”的运行闭环
- 展示一个面向具体领域的知识问答/任务执行助手

---

## 6. 功能需求与优先级

## P0：离线评测体系

### 6.1 背景

当前项目缺少对 Agent 能力的结构化评估。没有评测就无法回答：

- 任务完成率如何？
- 工具调用稳定性如何？
- 加入记忆/技能后是否真的提升？

### 6.2 目标

建立一套最小可行评测系统，用于对 Agent 的任务完成质量、工具成功率、延迟和失败类型进行量化。

### 6.3 功能要求

- 建立一个评测数据集目录，如 `backend/evals/`
- 至少定义 20~50 个典型任务
- 任务类型至少覆盖：
  - 文件读取与总结
  - 技能调用
  - 本地工具执行
  - 多轮上下文记忆
  - 知识检索问答
- 输出评测指标：
  - `task_success_rate`
  - `tool_call_success_rate`
  - `average_latency_ms`
  - `average_tool_calls`
  - `failure_category_distribution`

### 6.4 评测方法要求

- 采用“自我对比基线”而不是与 OpenClaw 直接比较
- 至少支持以下对比：
  - 无记忆 vs 文件记忆
  - 无技能协议 vs 技能协议
  - 无知识检索 vs 知识检索

### 6.5 验收标准

- 可以一键运行评测
- 可以生成 Markdown 或 JSON 报告
- 报告中必须体现：
  - 任务成功率
  - 平均延迟
  - 失败原因分类
  - 至少一个消融对比结果

---

## P0：运行可观测性

### 6.6 背景

当前项目可演示，但运行过程缺少可追踪性。面试官关心：

- 每次对话消耗多少 token？
- 出错卡在哪里？
- 工具调用了几次？
- 哪一步最慢？

### 6.7 目标

为每一次 Agent 运行建立结构化 trace。

### 6.8 功能要求

- 为会话运行生成唯一 `trace_id`
- 记录以下字段：
  - `session_id`
  - `user_id`（如果已实现）
  - `start_time / end_time`
  - `latency_ms`
  - `model_name`
  - `tool_calls`
  - `tool_failures`
  - `final_status`
  - `token_usage`（可获得时）
- 支持接入以下任一方案：
  - LangFuse
  - LangSmith
  - 本地 JSON 日志 + 可视化页面

### 6.9 UI 要求

前端至少提供轻量 trace 展示入口：

- 查看本次对话工具调用记录
- 查看失败原因
- 查看延迟与状态

### 6.10 验收标准

- 任意一次对话完成后都可追踪运行链路
- 发生错误时可以定位是：
  - 模型输出问题
  - 工具调用失败
  - 文件读取失败
  - 检索失败
  - 超时/重试失败

---

## P1：最小可行多用户隔离

### 6.11 背景

当前项目默认偏单用户。为了增强“产品化”说服力，需要证明系统考虑过用户隔离与上下文安全。

### 6.12 目标

不做复杂 SaaS 改造，仅实现最小可行的用户级隔离。

### 6.13 设计原则

- 优先延续“文件即记忆”的项目哲学
- 不强依赖 PostgreSQL
- 不引入过重的认证系统

### 6.14 功能要求

- 引入 `user_id`
- 存储目录改为按用户隔离，例如：
  - `backend/data/users/{user_id}/sessions/`
  - `backend/data/users/{user_id}/memory/`
  - `backend/data/users/{user_id}/workspace/`
- 默认支持通过 Header 或前端设置透传 `X-User-ID`

### 6.15 并发控制

- 为每个 `user_id` 引入异步锁
- 确保同一用户的写入串行化
- 避免会话与记忆文件竞态更新

### 6.16 可选增强

- 使用 SQLite 存储元数据（用户、会话索引、更新时间）
- 但不作为本阶段硬要求

### 6.17 验收标准

- 用户 A 和用户 B 的会话与记忆物理隔离
- 不同用户切换后，前端不会读到彼此上下文
- 至少一个测试用例证明隔离成立

---

## P1：失败分析与异常兜底

### 6.18 背景

AI Agent 的稳定性不取决于“永不出错”，而取决于“出错后是否可恢复、可解释”。

### 6.19 目标

建立错误分类体系和统一兜底策略。

### 6.20 功能要求

- 建立错误分类：
  - `tool_timeout`
  - `tool_invalid_input`
  - `model_invalid_format`
  - `memory_read_failure`
  - `knowledge_retrieval_failure`
  - `max_iterations_exceeded`
- 支持以下兜底机制：
  - 最大循环次数限制
  - 工具超时控制
  - 指数退避重试
  - JSON/结构化输出失败修复
  - 面向用户的友好失败信息

### 6.21 测试要求

- 针对核心工具增加异常边界测试
- 至少覆盖：
  - 非法 Shell 指令
  - 不存在的文件路径
  - 长文本解析失败
  - 检索无结果

### 6.22 验收标准

- 任意一类错误都能被分类记录
- 前端不出现静默失败
- 核心工具具备基础单测覆盖

---

## P1：垂直场景 Demo

### 6.23 背景

仅展示通用聊天框架说服力不足，需要一个“真的有用”的场景。

### 6.24 目标

基于当前通用框架，落地 1 个可以写进简历的垂直 Demo。

### 6.25 推荐方向（二选一）

#### 方向 A：面试问答助手

- 知识源：简历资料、面试题库、技术文档
- 能力：
  - 导入资料
  - 检索并生成问答
  - 多轮追问
  - 记录用户偏好与薄弱项

#### 方向 B：运维/工程文档助手

- 知识源：内部 Wiki、手册、项目 README、脚本说明
- 能力：
  - 检索答案
  - 结合 Shell 工具执行辅助操作
  - 输出排障建议

### 6.26 要求

- 有明确知识库目录
- 有 1~2 个定制 Skill
- 有至少 5 个典型任务案例

### 6.27 验收标准

- 可在演示中明确说明“它解决了什么问题”
- 可展示完整输入、检索、执行、输出闭环
- 至少能生成一组项目截图或 demo 录屏素材

---

## 7. 技术方案约束

### 7.1 必须延续的设计原则

- 本地优先
- 文件即记忆
- 透明可调试
- 前后端分离
- Agent 运行链路可解释

### 7.2 不建议引入的复杂度

- 完整 IAM 系统
- 重型分布式队列
- 复杂微服务拆分
- 过早引入多数据库与多缓存层

---

## 8. 里程碑规划

### M1：工程闭环基础版（1 周）

- 完成评测数据集与基础 runner
- 完成结构化日志与 trace_id
- 完成错误分类与失败记录

### M2：产品化增强版（1 周）

- 完成最小用户隔离
- 完成前端 trace/状态展示
- 完成基础工具单元测试

### M3：简历强化版（1 周）

- 完成垂直 Demo
- 输出评测报告
- 输出演示截图/录屏
- 形成简历项目描述定稿

---

## 9. 指标定义

本阶段建议追踪以下指标：

- `Task Success Rate`
- `Tool Call Success Rate`
- `Average End-to-End Latency`
- `Average Token Usage`
- `Retry Rate`
- `Failure Category Distribution`
- `Context Isolation Error Count`
- `Knowledge Retrieval Hit Rate`（如果实现）

---

## 10. 对简历的直接价值

完成本 PRD 后，Mini-OpenClaw 在简历中的定位将从：

- “做了一个 AI Agent 小项目”

提升为：

- “独立设计并实现了具备评测、观测、用户隔离与垂直场景落地能力的可观测 AI Agent 平台原型”

简历上重点可转化为：

- Agent 架构设计能力
- 评测与质量保障能力
- 可观测性与异常诊断能力
- 产品化与用户隔离思维
- 通用框架 + 垂直应用的完整闭环

---

## 11. 建议执行顺序

如果时间有限，建议按以下顺序推进：

1. 评测体系
2. 可观测性
3. 最小多用户隔离
4. 失败分析与测试
5. 垂直 Demo

原因：

- 前两项最能提升简历说服力
- 第三项最能应对“生产化”质疑
- 第四项最能体现工程素养
- 第五项最能增强“有用性”叙事

---

## 12. 附：本阶段一句话产品定义

Mini-OpenClaw 下一阶段的目标，不是成为功能最多的 Agent，而是成为一个“可评测、可观测、可隔离、可落地”的透明 AI Agent 工程样板。
